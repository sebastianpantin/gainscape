## Purpose

Tests that drive the real local Supabase stack: the Edge Functions over HTTP, SQL RPCs and RLS over the Supabase client, direct SQL assertions through `postgres`, and GoTrue email flows through Mailpit. They prove the server-authoritative pipeline (`complete-session`, `edit-session`, `delete-session`, replay, loot, crafting, events, social, account export and deletion, rate limits) end to end. The stack must be running; nothing here is mocked.

## For AI Agents

### Working In This Directory

- Import `local-stack.ts` for every stack interaction. Do not create a second Supabase client or hardcode URLs or keys; `env` comes from `supabase status`.
- Always create fresh users with `createTestUser()` (random `t_<hex>` username, `@example.test` email, confirmed). Tests share one database and most files run in parallel (4 workers), so isolation comes from unique users, never from truncating tables. Do not assume an empty DB or a quiet table. A file that edits or counts global rows must be listed in `INTEGRATION_FILES_SHARING_GLOBAL_STATE` in `vitest.config.ts` so it runs alone.
- Most files that import `db` end the pool in `afterAll(async () => { await db.end(); })` (`history-paging.test.ts` is the exception). Add it to new files.
- Shape session data with `aSet` and `payloadAt` from `session-support.ts` and send it with `postSession` or `postCompleteSession`. `postSession` asserts status 200 for you; use `postCompleteSession` directly when asserting a rejection.
- Use `ageSession` to move a session back in time instead of sleeping, and `seedRateLimitHits` to pre-fill rate-limit buckets.
- Time-dependent assertions use real timestamps; use `startsOnOneLocalDay(count)` so a batch of sessions lands on one Stockholm local date regardless of when the test runs.
- `hmacRngFor(userId)` reads `LOOT_SECRET` from `supabase/functions/.env.local` (written by `make functions`) so tests can reproduce the server's loot rolls.
- Schema or function changes need `make reset` before these tests pass; they exercise the migrations, not a snapshot.
- Never point this at a hosted project. `local-stack.ts` asserts the `.stack.env` project id matches the environment; run through `make` or `set -a; . ./.stack.env; set +a`.

### Testing Requirements

- Prerequisites: `make start` (stack plus served Edge Functions). Run all with `make test-integration` (it runs `make functions` first). Run one file with `npx vitest run tests/integration/rls.test.ts`; Edge Functions must already be served.
- Red-green loop: write the failing `it` in the file for the function or RPC (a new RPC with no home gets its own `<name>.test.ts`), run that single file, change the migration or function, `make reset` if SQL changed, rerun, then `make test-integration` and `make test-db`.
- Pure rule changes belong in `../domain/` first; add the integration case only to prove the server wires it correctly.
- Policy-, grant- and trigger-level checks that need no HTTP are better as pgTAP in `supabase/tests/`.

### Common Patterns

- `beforeAll` creates users and looks up `builtInExerciseId('<key>')`; each `it` posts a payload and asserts HTTP status, JSON body, then database rows via the tagged-template `db` client.
- Response bodies are `FunctionResponse` (`status`, `body`, `rawBody`, `headers`); error assertions check `body.error`.
- `normalizedSnapshot(userId)` plus `rebuildCaches(userId)` compares live state against a rebuild, used to prove replay and edits are consistent.
- RLS tests call as a user client (`user.client`) or `anon`; privileged setup uses `admin` or `db`.
- Email flows: note `since = new Date()`, trigger an auth action, `waitForEmail(to, { subject, since })`, then `authLinkFrom(message)`. Fresh addresses keep mailboxes apart, so nothing is deleted.
