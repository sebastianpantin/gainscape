# e2e

**Parent context:** `../AGENTS.md`
**Generated:** 2026-10-01 · **Updated:** 2026-10-10

## Purpose

Playwright end-to-end suites that drive the real web app against the real local Supabase stack in a Pixel 7 Chromium (`make e2e`) and an iPhone 14 WebKit (`make e2e-webkit`). The specs in this directory run against the Vite dev server over https with service workers blocked (`playwright.config.ts`). The `pwa/` subdirectory runs against a production-style build with service workers allowed (`playwright.pwa.config.ts`). Shared helpers are in `support/`.

### Working In This Directory

- Configs: `../playwright.config.ts` (`testDir: 'e2e'`, `testIgnore: ['pwa/**', 'pages/**']`, timeout 90 s, `fullyParallel: false` so tests inside a file run in order unless the file opts in with `test.describe.configure({ mode: 'parallel' })` (`a11y.spec.ts`, so CI shards can split it), projects `chromium` (Pixel 7, system `chromium` through `CHROMIUM_PATH`) and `webkit` (iPhone 14), `ignoreHTTPSErrors`, `serviceWorkers: 'block'`, web server `npx vite web --host` reused if already running except on CI). Every config spreads `runSettings` and `failureArtifacts` from `support/run-settings.ts`: locally no retries and the `list` reporter; on CI (`CI` set) `forbidOnly`, one retry (a retried pass is reported as flaky) and the `github`, `list` and `html` reporters; trace and screenshot kept on failure, no video (recording every test doubles the CPU time). And `../playwright.pwa.config.ts` (for `pwa/`).
- Both configs call `assertStackEnvironment()` at load; a mismatch with `.stack.env` aborts the run.
- Every spec registers its own user with a unique name (for example a `prefix_` plus `Date.now().toString(36)`, passed to `register`). Never share users or rely on prior data. Specs reach the database directly through `support/db.ts` for setup and verification (items, scroll counts, forced edits).
- Locate by role and accessible name (`getByRole`, `getByLabel`, then visible text with `getByText`) so tests double as accessibility checks. No test ids: ESLint fails on `getByTestId` here and on `data-testid` in `web/src`. When a value has no role or name, give it one in the app. The patterns in use:
- Label and value pairs are `<dl>` terms and definitions. Read the value with `definitionOf(scope, term)` from `support/app.ts`: the `<dd>` after the `<dt>` whose text is exactly `term` (`definitionOf(page, 'Bodyweight')`, `definitionOf(page.getByRole('region', { name: 'Time zone' }), 'Current')`).
- Workout rows are list items named `Set N` and `Bout N` (`<exercise>, set N` inside a superset round); reach them with `setRow(scope, n)`, `setRows(scope)` and `boutRow(scope, n)` inside `exerciseCard(page, name)`, never with `li.set-row` or `.nth()`. A done set is a pressed `Done set N` button (`doneSetButtons`). Collection rep-max slots are list items in the `Rep maxes` list; `exactRepMaxes(card)` keeps the ones a set at exactly those reps filled. A set's plate chips are an image named `N plates each side`. The warm-up toggle and Remove sit in the row's options menu (`openSetOptions(row, n)`); check a warm-up flag with `warmupBadge(row)`.
- A computed total that changes on screen is a named `<output>`: `getByRole('status', { name: 'Workout XP' })` on the workout detail.
- The profile card badge is an image named after its colour: `getByRole('img', { name: 'Blue badge', exact: true })`. Badges elsewhere are decorative (`aria-hidden`) and have no role.
- Plain text such as the bio, the detail line or the record preview is matched with `getByText(text, { exact: true })` inside its named region (`getByRole('region', { name: 'Profile', exact: true })`, `getByRole('region', { name: 'How your records appear' })`).
- A database read after a UI action races the write: assert it with `await expect.poll(() => sessionCount(username)).toBe(1)`, not `expect(await sessionCount(username)).toBe(1)`. The same goes for values read from the page with `weightsIn`/`repsIn` or from browser storage. A check that something did not change (a count that stays put, no events) stays a plain `expect(await …)`: a poll would pass on its first read and only pretend to wait.
- Long program flows (`program-flow-*.spec.ts`) wrap each phase in `test.step` with a descriptive name: following the program, each seeded stretch of sessions and each prescription assertion, so a failure names the week and lift.
- Long tests set `test.setTimeout(...)` locally (for example `a11y.spec.ts` 150 s, `token-refresh.spec.ts` 180 s). Do not raise the global timeout; split a test that outgrows its budget into tests with their own users so they run on separate workers.
- No comments and no `test.skip`.

### Testing Requirements

- Prerequisites: `make start` (stack plus Edge Functions). `make e2e` runs `make functions`, then `npx playwright test --project=chromium $(E2E_ARGS)` with `CHROMIUM_PATH` set to the system `chromium` if found (CI passes it empty to use Playwright's own browser). `make e2e-webkit` runs the `webkit` project; Playwright's WebKit build needs Ubuntu system libraries, so on other hosts run it in the `mcr.microsoft.com/playwright` image of the installed Playwright version with `--network host` and the Docker socket and CLI mounted (the stack guard calls `supabase status`), or leave it to the weekly e2e workflow. The web server starts itself. While another Playwright run is active, pass a separate `--output` directory so the runs do not share `test-results/`.
- One spec: `npx playwright test e2e/history.spec.ts`; one test: add `-g "part of the title"`. Use `--headed` or `--trace on` to debug; traces are retained on failure in `test-results/`.
- Red-green loop: add a failing `test(...)` in the spec for the screen (new screens get a new `<area>.spec.ts`), run only it, implement in `web/src`, rerun, then `make e2e`. Push logic into `web/src/lib/*-rules.ts` and cover it in `../tests/web/` first when possible; keep e2e for wiring and flows.
- A change to the service worker, shell, manifest or update flow is covered by `pwa/`, not here.

### Common Patterns

- `register` (creates a confirmed account through the admin API with the browser's time zone, then signs in through the form; only `auth.spec.ts` and `registration.spec.ts` drive the sign-up form, with `submitRegistration`), `signIn`, `openTab`, `openFromProfile`, `addExercise`, `chooseFromMenu`, `logExercise`, `logWorkout`, `logBench`, `finishWorkout`, `openLatestWorkout` from `support/app.ts` for flows, and `openManageProgram`, `cycleSummary` from `support/program-enrollment.ts`. Reuse them instead of inlining the start, finish and reveal steps, and move a helper that a second spec needs into `support/` rather than copying it.
- Import `test` and `expect` from `support/fixtures.ts`, never from `@playwright/test` (types still come from there). Its `context` and `newPerson` fixtures fail a test on any uncaught page error (`pageerror`) in their pages, checked before the contexts close so the failing test keeps its trace. On WebKit it ignores "… due to access control checks." reports, which WebKit raises for fetches a reload or navigation cancels. A spec that depends on one engine's behaviour pins it with `test.use`: `settings-install.spec.ts` uses the Pixel 7 user agent because `beforeinstallprompt` is Chromium's (an iPhone user agent takes the iOS manual-install path). In contexts with `serviceWorkers: 'block'` it makes `navigator.serviceWorker.register` reject like a browser with service workers disabled, because Playwright's block resolves it with `undefined`.
- Two users or devices: call the `newPerson()` fixture from `support/fixtures.ts` once per person (`friends.spec.ts`, `auth.spec.ts`, `a11y.spec.ts`); it opens a fresh context and closes every context it opened when the test ends, even on failure. Do not call `browser.newContext()` directly; two tabs: `context.newPage()` (`multi-tab.spec.ts`).
- Simulating failures: route interception for outages and 401s (`token-refresh.spec.ts`), `breakIndexedDbOpen` and `setIndexedDbBroken` for storage failures, `resignedWithAnotherKey` for bad tokens.
- Conflicts with another device: `editElsewhere` or `sessionRow` from `support/db.ts`.
- Email steps: `waitForEmail` and `authLinkFrom` from `support/mailbox.ts`.
