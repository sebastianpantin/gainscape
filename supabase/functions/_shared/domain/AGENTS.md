## Purpose

The pure game engine of gainscape. It turns logged sets into effective reps, XP split across skills, levels, strength estimates, personal records, loot drops and friend-feed events. The same files run in Deno inside the Edge Functions (imported through `../domain/index.ts`) and in the browser and Vitest (imported through the `@domain/*` alias defined in `tsconfig.json` and `vitest.config.ts`). The web app uses it for offline XP previews and display rules, the server uses it as the authority when a session completes, is edited, or has its caches rebuilt. Everything here is deterministic: the same inputs and the same `BalanceConfig` always produce the same outputs.

## For AI Agents

### Working In This Directory

- **Purity is non-negotiable.** A domain file may import only sibling files as `./name.ts`. It must not touch `Deno`, `process`, `window`, `document`, `localStorage` or `require`, and must not read the clock, call `Math.random`, or do I/O. Take time as a parameter (see `isWithinEditWindow(startedAt, now)`) and randomness as an `Rng` (see `LootRngFor`). Two things enforce the import and globals rules: `tests/domain/purity.test.ts` (checks every `.ts` file here for non-sibling imports and runtime globals, including `require`) and the ESLint `no-restricted-globals` override in `eslint.config.js` (all of them except `require`). Nothing enforces the clock and `Math.random` rule; reviewers must check it. Anything needing Deno, crypto or the database belongs one level up (`../loot-seeds.ts`) or in `../stores/`.
- **New modules need an `index.ts` export.** Consumers import from `index.ts` or `@domain/index.ts`. The purity test globs the directory, so a new file is checked automatically.
- **No comments, ever.** The `gainscape/no-comments` lint rule applies. Name constants (`SFC32_DISCARDED_OUTPUTS`, `CHANCE_DECIMALS`) instead of explaining magic numbers.
- **The pipeline is a list of `Step`s.** A step is `(ctx: SessionContext) => SessionContext`. `trackStrength` lives in `strength.ts` and `detectPersonalRecords` in `records.ts`; both import the `Step` type from `pipeline.ts`, and `pipeline.ts` imports them back to build `DEFAULT_STEPS`. Step order matters: `resolveSets`, `trackStrength`, `checkFatigue`, `detectPersonalRecords`, `awardXp`, `awardSessionBonuses`, `applyXp`, `detectLevelUps`. `awardSessionBonuses` runs when the session has a gear loadout or a `session.challenge`. It judges the challenge with `judgeChallenge` against the stored e1RM snapshot, sums each skill's base parts over the session, adds `gearBonusXp` (with `session.gearLoadout`) and, for a passed challenge, `challengeBonusXp` of that base sum, spreads the total over the parts by largest remainder (ties to the lower set position) and reports `gearBonusBySkill`, `challengeBonusBySkill` and `challengeVerdict` (only the part of each bonus that fits above the base XP under the `maxXp` cap, the challenge bonus first, so 0 when base XP alone reaches it). Both bonuses are computed on base XP and added, so the total is base × (1.25 + gear%), never compounded. A failed challenge pays nothing but still reports its verdict. History-only sessions run only `resolveSets` and produce no XP, records or loot.
- **Determinism and loot seeds.** Loot rolls take an injected `LootRngFor`. Production builds it in `../loot-seeds.ts`: HMAC-SHA256 of `lootSeedMessage(userId, setId, kind)` keyed by the `LOOT_SECRET` env var, fed to `sfc32FromSeed`. The same set always rolls the same result, so a replay or edit never re-rolls. Rolls already recorded are skipped through `LootDayState.alreadyRolled` and `lootRollKey`. Do not change `lootSeedMessage`, the sfc32 constants, the order of `rng.next()` calls in `rollSessionLoot`, `pickEntry`'s key-sorted entry order, or `quantityFor`; each silently changes existing players' drops.
- **Iteration order must be explicit.** Sets sort by `position`, skills by `sortOrder`, sessions through `compareSessionKeys`, loot entries by `itemKey`. Never rely on Map or object key order for results that are persisted.
- **`balance.ts` is the tuning surface.** `DEFAULT_BALANCE` fields: `xpPerEffectiveRep` (165, the main pacing lever), `effectiveRirWindow`, `effortLevelRir` (easy 5, hard 3, near_failure 1, failure 0; stored level efforts hold this RIR, so changing it needs a migration of `sets.effort_value`), `coldStartXpPerSet`, `coldStartMaxSetsPerExercise`, `fatiguePerHardSet`, `fatigueToleranceReps`, `rirTrustMargin`, `maxRirForStrength`, `epleyMaxRepsToFailure`, `e1rmWindowDays`, `maxStrengthGainPerSession`, `intensityBonusStart/Full/Max`, `prMinGainKg` (a record must beat the stored slot by at least this much), `maxXp`. External sets with no load earn no XP. `DEFAULT_LOOT` controls daily roll caps, hit chance (`baseChance` + `badLuckStep` per dry roll, capped at `maxChance`). `DEFAULT_FEED` controls which level-ups and drop rarities reach the friends feed.
- **Changing balance constants has two consequences.**
  1. **`make sim-check`** runs `tests/balance/balance-bands.test.ts`, which simulates four lifter profiles (`scripts/balance/`) with the committed `DEFAULT_BALANCE` and asserts the design bands in `scripts/balance/bands.ts`: a balanced 3x/week lifter takes 2 to 3 years to reach legs level 99 and ends week 1 between legs level 20 and 40, hypertrophy and strength lifters stay within 15% of each other, and a casual lifter is slowed in proportion to effort. It takes about 1 s and needs no stack. `make sim` prints the report and `scripts/balance/tune.ts` is the tuning helper.
  2. **`BALANCE_VERSION` must be bumped** whenever a change alters stored derived values (XP, RIR, e1RM, effective reps, records). Sessions store `balance_version` and `derived_balance_version`. After a bump, `replayFrom` in `../stores/replay.ts` throws `HttpError(503, 'rebuild_required')` for any user whose sessions are behind (`hasStaleDerivedSessions`) until the `rebuild-caches` Edge Function replays them. Run **`make rebuild-caches`** (`scripts/rebuild-caches.mjs`) against the local stack to replay every profile with sessions behind the new version (`make rebuild-caches ALL=1` replays every profile with data). Bump `LOOT_VERSION` when loot configuration semantics change. `revocationReason` never revokes a drop rolled under an older `LOOT_VERSION` as `no_longer_qualifies`, so a rule change keeps players' existing drops; removed sets and deleted sessions still revoke.
- **`xp_awarded` is base XP.** `SetResult.xp` (stored as `sets.xp_awarded`) is the XP before the gear bonus, while the skill parts (stored as `set_skill_xp`) include it. Once a session has a gear bonus, a set's `xp_awarded` no longer equals the sum of its `set_skill_xp`. Sum `set_skill_xp` (or `summary.xpBySkill`) for skill totals.
- **The gear map and percent are balance.** Changing `GEAR_SLOT_SKILLS`, `ITEM_TIERS` order or `gearBonusPercentAtFullTier` changes the XP of every replayed session that has a `gear_loadout` snapshot, so it needs a `BALANCE_VERSION` bump and `make rebuild-caches`. `gearBonusPercentAtFullTier` must stay a non-negative integer.
- **The challenge bonus, load step and judge rules are balance.** Changing `challengeBonusPercent`, `CHALLENGE_LOAD_STEP_KG` or what `judgeChallenge` counts changes the verdict or the XP of every replayed session that has a `sessions.challenge` snapshot, so it needs a `BALANCE_VERSION` bump and `make rebuild-caches`. `challengeBonusPercent` must stay a non-negative integer. The `'up'` rounding direction exists only on `roundLoad` and is not a `RoundingMode`: `RoundingSetting` and the user's plate rounding stay `nearest` or `down`; the judge floor itself rounds `'down'`.
- **A challenge is judged from its snapshot only.** The verdict reads `session.challenge` (definition and e1RM snapshot taken at sync) and the replayed sets, never the live catalog, so an edit can flip the verdict but an earlier session cannot.
- **Rounding.** Use `roundTo` from `math.ts` for decimal rounding and `roundXp` from `xp.ts` for whole XP (loads to 2 decimals, chances to 5, intensity bonus to 6). `setXp` and `splitXp` use integer XP only; do not introduce fractional XP.
- **Types are shared with the web.** `web/src/lib/*-rules.ts`, `web/src/offline/` and workout features import this directory. Changing a type or export here can break the web type-check; run `make typecheck`.

### Common Patterns

- Functions are small, pure, and exported by name; internal helpers stay unexported (`roundHalfUp`, `slotsFor`, `levelEvents`, `dropFrom`).
- Config is always an explicit parameter (`cfg: BalanceConfig`, `cfg: LootConfig = ...`); no module reads `DEFAULT_*` implicitly except as a parameter default (`events.ts`).
- Pipeline state is immutable: each step returns `{ ...ctx, sets }` or `{ ...ctx, state }` rather than mutating.
- Domain errors are `Error` subclasses in `errors.ts`; invalid numeric ranges throw `RangeError`.
- Constants carry intent in their name (`FULL_SHARE_BASIS_POINTS`, `FLOAT_NOISE_DECIMALS`, `GUARANTEED_CHANCE`).
- Skill identity is split: `id` (uuid) for persistence and `key` (string like `legs`) for summaries and feed payloads.

## Dependencies

### Internal

- Imported by `../stores/*.ts`, `../loot-seeds.ts`, `../session-payload.ts` and the Edge Functions (`complete-session`, `edit-session`, `delete-session`, `rebuild-caches`).
- Imported by `web/src` through `@domain/index.ts`.
- Imported by `scripts/balance/*` (simulation) and `tests/domain`, `tests/balance`, `tests/web`.
- `crafting.ts` item tier and gear slot lists are checked against the catalog by the catalog validator in `scripts/catalog/`.

### External

None. The directory has no third-party or runtime dependencies by design.
